# 개발 성장 기록

개발 결과와 사용자가 같은 결정을 이해하고 재현할 수 있는 기록을 함께 남긴다. 기록 때문에 원래 작업을 계획 단계에서 멈추거나 범위를 확대하지 않는다.

## 위치와 시점

- AGENTS.md와 기존 문서 구조를 먼저 읽는다. 기본은 `docs/development/YYYY-MM-DD.md`, 진입점은 `docs/development/README.md`다. 사용자 현지 날짜를 사용하고 같은 날의 기록에 누적한다.
- 새 실질적 요청마다 질문 원문·요약·의도 해석(추정)을 기록하고, 작업 후 선택 이유·실제 변경·검증·한계를 갱신한다. 진행 중인 결과를 완료로 쓰지 않는다.
- 제품 콘텐츠와 개발 회고를 분리한다. 학습 데이터로 변환되는 README에 회고를 섞지 않는다.
- 확인 가능한 원문만 쓰고 줄이면 발췌/요약이라고 표시한다. 비밀번호·토큰·불필요한 개인정보는 가린다. 과거 응답이나 사용자의 이해도를 지어내지 않는다.

## 기술과 선정 목적

실제로 사용한 기술을 변경 파일과 연결해 설명한다. 어디에 썼는지, 해결한 문제, 현재 조건에서 고른 이유, 다른 도구가 유리한 조건, 알아둘 개념, 작은 재현 연습과 성공 기준을 남긴다. 단순 수정은 짧게 쓰고 중요한 설계·운영 판단을 자세히 쓴다. 사용하지 않은 도구나 수행하지 않은 검증을 완료처럼 쓰지 않는다.

구조/코드 규칙을 변경했다면 기존 지침을 보존하며 AGENTS.md나 연결된 구조 문서에 반영한다. 현재 프로젝트의 기술·Git 금지 같은 제약을 다른 프로젝트의 보편 규칙으로 복사하지 않는다.

## 승인 요청과 흐름

실제 승인 요청이 있었거나 사용자가 승인 흐름을 물었다면 [상세 기록 양식](references/record-template.md)을 읽는다.

- 행동·대상·권한 범위·실제 요청 문구와 필요 근거를 남긴다. 환경의 파일/네트워크 권한 제한, 지침/스킬의 명시 조항, 개인적 선호를 구분한다. 지침 때문이면 파일 경로와 해당 조항을 인용한다.
- 승인 없이 할 수 있었던 준비와 검토 가능한 파일, 요청한 행동, 더 좁은 대안, 실행 결과와 검증을 연결한다.
- 요청함/명시적 승인/기존 허용 규칙 또는 환경에서 실행됨/수단 확인 불가/거절/미응답을 구별한다. 실행 성공만 보고 사용자가 버튼을 눌렀다고 쓰지 않는다. 과거 승인 건수·시각·응답을 복원해 만들지 않는다.
- 자동 승인 검토가 거절하면 해당 행동과 제공된 이유를 기록한다. 다른 도구로 같은 권한을 우회하지 않는다.
- 기록을 위해 새 승인 단계를 만들지 않는다. 이미 허용된 범위의 읽기·가역 수정에 재승인을 요구하지 않는다. 필요한 외부 쓰기·전송·배포에는 해당 작업의 실제 권한 규칙을 따른다. 기록이 승인을 대신하지 않는다.
- 승인 요청이 없으면 없다고 짧게 쓰거나 항목을 생략한다. 사용자 답이 필요한 단계에서 시간 경과를 승인으로 보지 않는다.

## 학습과 검증

- 검증은 명령·환경·성공/실패·증거 파일과 연결한다. 정적 검사·단위 테스트·브라우저 확인·실기기·운영 부하 시험을 구분한다.
- 실제 변경에서 1~3개 학습 포인트만 골라 짧은 연습을 제안한다. 새 작업이나 비용을 강제하지 않는다.
- 기술을 조사했다면 읽은 공식 근거를 남긴다. 사용자 후기는 주장·표본 한계·프로젝트에 적용한 가설을 구분한다.
- 비공개 내부 추론 대신 검토 가능한 결정 요약과 관찰 근거를 제공한다.
- 일지가 길어지면 기술 학습은 `docs/learning/`, 구조/운영은 기존 문서로 분리하고 링크한다. 불필요한 파일을 늘리지 않는다.
- 최종 답변은 기록 위치와 중요한 결정만 간단히 알린다.
