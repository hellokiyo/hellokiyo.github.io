# 개발 학습과 승인 기록 양식

실제 있는 항목만 작성한다. 형식을 채우려고 승인이나 검증을 만들어내지 않는다.

## 요청과 결과

질문 원문/표시된 발췌 → 요약 → 의도 해석(추정) → 문제와 완료 조건 → 선택·대안·이유 → 변경 파일과 동작 → 검증·한계.

## 승인 요청이 있었다면

| 항목 | 기록 내용 |
|---|---|
| 행동과 범위 | 대상 파일/서비스/프로세스, 변경·전송·비용 범위 |
| 목적 | 사용자 요청에 왜 필요한가 |
| 필요 근거 | 실제 환경 제한 또는 정확한 지침·스킬 조항 |
| 준비 결과 | 승인 전에 만든 검토 가능한 파일과 검사 결과 |
| 요청 내용 | 실제 질문과 요청 권한, 지속 허용 규칙 제안 여부 |
| 승인 상태 | 명시적 승인/기존 허용/수단 미확인/거절/미응답 |
| 실행 결과 | 실제로 어디까지 실행했는가, 실패/우회하지 않은 경로 |
| 검증 | 무엇을 확인했고 무엇은 확인하지 못했는가 |

흐름: 요구 확인 → 허용 범위에서 준비 → 필요한 구체적 행동의 승인 요청 → 허용 범위 내 실행 → 검증 → 기록. 사용자 응답이 필요한 단계는 미응답 상태로 유지한다.

## 알아둘 기술

기술·사용 파일·담당 책임 / 개념을 쉬운 말로 / 지금 선택한 이유 / 대안을 고를 조건 / 짧은 실습과 성공 기준.

예: getState로 화면을 분리했다면 가져오기 후 객체가 교체될 때 기존 참조가 낡는 이유를 설명한다. 새 상태를 넣었을 때 검색/읽음 화면이 새 값을 표시하는지 확인하는 연습을 제안한다. 수행하지 않았다면 제안이라고 표시한다.

## 다음 확인

중요한 가설·미결정 조건·추가 검증만 남긴다. 계획과 완료를 섞지 않는다.
